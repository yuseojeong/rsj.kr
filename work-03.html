01 / OVERVIEW

어떤 문제를, 어떻게 풀고자 했는지.

연OX는 지인에게 꺼내기 어려운 연애 고민을 익명으로 나누고, 다양한 의견과 후기를 통해 자신의 관계를 돌아보는 커뮤니티 앱입니다. 관계가 불편해도 쉽게 정리하지 못하거나 연애 경험이 적어 혼자 판단하기 어려운 여성을 기획의 출발점으로 삼았습니다. 컨셉·정책·화면부터 데이터·API 설계까지 바이브 코딩으로 구체화했으며, 현재 마케팅 콘텐츠를 준비하고 있습니다.

01발견한 문제

관계의 불편함을 느껴도 쉽게 헤어지지 못하면 같은 고민을 친구에게 다시 꺼내기 어렵습니다. 연애 경험이 적어 판단 기준이 없거나, 반복해서 조언하는 친구의 부담까지 신경 쓰며 혼자 감당하기도 합니다.

02검증할 가설

익명 사연과 가벼운 OX 투표로 말하기·답하기의 부담을 낮추면 다양한 의견이 모일 것입니다. 후기 요청과 알림은 비슷한 고민의 이후 이야기를 확인하러 돌아올 이유가 될 것이라 보았습니다.

03설계 방향

초기 기능 요구사항을 먼저 정하고, 익명 사연 → OX 투표 → 댓글 → 후기의 참여 흐름을 구체화했습니다. AI 개발 규칙과 모바일 프로토타입을 바탕으로 정책·데이터·API를 연결하고, 프롬프트 관리와 테스트를 위한 운영 어드민도 제작했습니다.

02 / DELIVERABLES

서비스가 되기까지, 기획의 과정.

컨셉·문제정의와 초기 요구사항에서 AI 개발 규칙, 프로토타입, 정책, 모바일 UX, 데이터·프롬프트, API까지 — 바이브 코딩의 7단계와 현재의 마케팅 준비를 정리했습니다.

02 · AGENTS.md · AI 개발 규칙

한 화면도 컴포넌트와 역할별로 나눠 코드를 작성하도록 규칙을 정했습니다.

AGENTS.md 코드 작성 전 우선 참조
_area화면 레이아웃

정적 뷰와 표현

_action사용자 행동

인터랙션과 상태

_lib데이터 통신

Supabase 순수 함수

거대 단일 파일 금지임의 더미 배열 금지UI에서 DB 직접 호출 금지
실제 화면별 폴더 구조

한 화면을 한 파일에 몰아넣지 않고,
컴포넌트와 역할별로 분리했습니다.

화면 단위인 screens/chat 안에 화면 영역, 컴포넌트, 액션, 상태 등을 나눴습니다. 상세 화면인 detail도 독립된 폴더 안에서 같은 방식으로 구성하도록 했습니다.

AI가 새 기능을 만들 때도 화면 전체를 다시 작성하는 대신, 해당 컴포넌트와 역할에 맞는 위치에 코드를 추가하도록 구조화했습니다.

src/
└─ screens/
   └─ chat/
      ├─ _action/
      ├─ _area/
      ├─ _component/
      ├─ _handler/
      ├─ _lib/
      ├─ _state/
      ├─ _svg/
      └─ detail/
         ├─ _action/
         ├─ _area/
         ├─ _component/
         ├─ _lib/
         ├─ _model/
         ├─ _state/
         ├─ _svg/
         └─ ChatDetailScreen.tsx
고민
AI와 페어 프로그래밍을 진행하다 보니, AI가 파일 하나에 1,000줄이 넘는 모놀리식(Monolithic) 코드를 짜거나, 임시 더미 데이터를 남발하고, 무분별한 useState를 사용하여 추후 유지보수가 불가능해지는 치명적인 문제가 발생했습니다.
액션
AI가 마음대로 코드를 짜지 못하도록, 프로젝트 최상단에 AI가 코드 작성 전 무조건 0순위로 읽어야 하는 AGENTS.md (AI 개발 규격 가이드)를 설계하여 주입했습니다.
구체적 해결

아키텍처 강제 분리: 화면 레이아웃만 담당하는 정적 뷰(_area), 사용자 인터랙션과 상태를 관리하는 모듈(_action), Supabase 통신 순수 함수(_lib)로 컴포넌트 역할을 엄격히 분리하도록 명시했습니다.

안티패턴(Anti-Patterns) 원천 차단: "1,000줄 넘는 거대 단일 파일 작성 금지", "가짜 하드코딩 배열 선언 금지", "UI 파일 안에서 DB 직접 호출 금지" 등 AI가 자주 실수하는 13가지 🚫금지 조항을 명문화하여, AI가 스스로 코드를 생성할 때 이 규칙을 강제로 검열하도록 통제력을 확보했습니다.

04 · 정책 설계 · 요구사항 구체화

투표·댓글·익명 식별의 예외를 발견하며 참여 규칙을 구체화했습니다.

  • 투표 횟수 한 사용자당 같은 글에 한 번만 투표할 수 있습니다.
  • 댓글 접근 해당 글에 투표한 뒤에만 댓글을 보고 작성할 수 있습니다.
  • 익명 식별 같은 글에서는 같은 작성자의 익명 번호를 유지합니다.
  • 공통 UI 모달을 개별적으로 늘리지 않고 공통 바텀시트로 통일합니다.
고민
서비스가 커지면서 모달(Modal) 창이 무분별하게 튀어나오고, 댓글 창에서는 똑같은 사람이 글을 써도 '익명1', '익명7'처럼 닉네임이 매번 바뀌어 유저 간 혼란을 주는 엣지 케이스가 발견되었습니다.
액션
이를 방지하기 위해 공통 UI 정책과 데이터 렌더링 규칙을 요구사항 정의서로 세밀하게 픽스했습니다.
구체적 해결

모달 남발을 막기 위해 바텀시트 모달을 공통 컴포넌트로 규격화했습니다.

익명 유저 시스템 고도화: 단일 게시글 내에서 동일한 작성자가 여러 번 글을 남길 때, 무작위 이름이 아닌 user_id를 추적해 '익명1', '익명2'와 같이 고유 번호가 일관되게 부여되도록 Map 객체를 활용한 식별자 매핑 로직을 설계했습니다.

고민
바텀시트(@gorhom/bottom-sheet) 내부에 긴 댓글 리스트를 띄웠을 때, 스크롤 제스처가 잠겨버리거나(Locked) 하단으로 스와이프해도 창이 닫히지 않는 네이티브 충돌 이슈가 발생했습니다.
액션
AI는 일반 웹 프론트엔드 방식의 해결책만 제시했기에, 직접 라이브러리의 모바일 제스처 동작 방식을 뜯어보고 구조를 재설계했습니다.
구체적 해결
일반 ScrollView 사용을 전면 금지하고, 바텀시트 전용 BottomSheetScrollView를 최상위 스크롤러로 강제 바인딩하도록 로직을 수정했습니다. 또한 하단 댓글 입력창이 키보드 활성화 시 애니메이션 프레임(60fps)에 맞춰 부드럽게 밀려 올라가도록 bottomInset과 SafeArea를 정교하게 계산했습니다.

'연애오답'의 핵심 기능인 'AI O/X 선택지 자동 추천'을 구현할 때, 유저의 사연 글 맥락을 파악하지 못하고 너무 뻔하거나 엉뚱한 O/X 질문이 추천되는 문제가 있었습니다.
액션
단순 API 연결을 넘어, AI 모델이 문맥의 의도를 정확히 파악하도록 프롬프트 엔지니어링(Prompt Engineering)을 고도화했습니다.
구체적 해결
프롬프트 작성 시 단순히 "O/X 질문을 만들어줘"가 아니라, 사연의 갈등 상황별 최적의 O/X 선택지를 매핑한 다양한 퓨샷(Few-shot) 예시 데이터를 프롬프트에 주입하여 응답 퀄리티를 기획 의도에 맞게 극대화했습니다.

운영 어드민 · 프롬프트 적용과 테스트

AI로 제작한 관리 화면
고민
프롬프트를 수정할 때마다 코드와 테스트 도구를 오가는 과정이 번거로웠습니다. 운영 단계에서도 게시글·신고·문의 관리가 필요할 것이라 판단했습니다.
액션
AI와 함께 어드민을 제작하고, 프롬프트를 저장·적용하는 편집 영역과 실시간 테스트 영역을 한 화면에 배치했습니다.
구체적 해결
O/X 생성과 게시글 검수 프롬프트를 구분했습니다. 테스트 제목·본문으로 Gemini를 호출하고 JSON 응답을 확인해, 문구 수정과 결과 검토를 같은 흐름에서 할 수 있게 했습니다.
검수 프롬프트의 판단 기준
판단 대상구체화한 기준응답 연결
일상적인 짧은 글짧은 문장·줄임말·초성이라는 이유만으로 차단하지 않음PASS · 일상 표현과 도배를 구분
도배·광고·부적절한 표현무작위 반복 문자열 / 상업적 홍보 / 과도한 비속어와 비방을 분리사유 코드와 지정된 안내 문구 반환
출력 형식is_approved / reason_code / message를 가진 JSON승인 여부와 사용자 안내를 일관되게 연결

액션
문서를 읽는 즉시 테스트까지 가능한 Swagger UI 대화형 API 명세서를 도입했습니다.
구체적 해결

위 UI는 확인 흐름을 재구성한 도식이며, 실제 엔드포인트나 테스트 실행 로그를 나타내지 않습니다.

배운 점

01AI와의 협업에도 설계 기준이 필요

초기에 요구사항을 정하는 것만으로는 AI가 만드는 코드 구조까지 일관되게 유지되지 않았습니다. AGENTS.md로 뷰·행동·통신의 역할과 금지 패턴을 명시하고, 프롬프트 수정과 테스트를 위한 어드민까지 만들어 반복 작업의 기준을 마련했습니다.

02화면 완성과 서비스 연결은 다른 단계

더미 데이터로 보이는 화면에서 실제 데이터가 오가는 서비스로 이어지려면 DB 구조, 접근 권한, API 연동을 각각 확인해야 했습니다. 프로세스를 단계별로 나누며 각 산출물의 역할을 정리했습니다.

03홍보도 기획 의도와 연결하기

기능을 많이 보여주는 것보다 왜 이 공간이 필요한지를 전달하고자 했습니다. 말하기의 망설임에서 시작해 익명 참여와 후기의 가치를 소개하는 콘텐츠로 마케팅을 준비하고 있습니다.
